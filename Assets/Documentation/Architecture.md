# Архитектура проекта и правила добавления фич

Проект разделён на Infrastructure, Application, Meta и будущий Core. Фичи построены по MVP. Общий UI-слой управляет жизненным циклом окон, а Zenject собирает зависимости. Сейчас существует только меню; игровых механик в Core нет.

## Открытие окна

Код сценария обращается к сервису по типу презентера:

```csharp
await uiService.Open<MenuPresenter>();
await uiService.Close<MenuPresenter>();
```

В GameInstaller задаётся соответствие презентера, конкретной View, её интерфейса и адреса Addressables:

```csharp
windows.Register<MenuPresenter, MenuView, IMenuView>("ui/menu", UiLayer.Windows, isDefault: true);
Container.Bind<MenuModel>().AsTransient();
Container.Bind<IMenuActions>().To<MenuActions>().AsSingle();
```

Отдельная фабрика для каждого окна не нужна. UiService находит регистрацию, загружает prefab, создаёт View и выполняет её инъекцию до Awake. Затем общая регистрация создаёт Presenter через Zenject, базовый презентер получает View и проводит окно через инициализацию и открытие. Презентер фичи не загружает ассеты и не работает с DiContainer.

На тип презентера существует не более одного экземпляра в истории. Повторный Open текущего окна возвращает его без новой инициализации и анимации. Open окна, которое уже есть глубже в истории, возвращает к этому экземпляру и удаляет записи над ним в том же слое. Операции навигации сериализованы; во время перехода UI-ввод отключён. После удаления окна из истории его ресурсы освобождаются, а следующий Open создаёт новые Model, View и Presenter.

## Слои окон и история

UiLayer.Windows — основные окна, UiLayer.Popups — попапы поверх них. Слой задаётся при регистрации в инсталлере. UiViewLoader автоматически создаёт отдельные RectTransform-контейнеры под UI root, упорядоченные по числовому значению слоя. В prefab не нужно самостоятельно настраивать Canvas sorting order; дочерние Canvas не должны обходить общий порядок через overrideSorting.

Каждый слой хранит собственную историю. Новое окно закрывает анимацию предыдущего и скрывает его GameObject, сохраняя Presenter, Model и View. Поэтому при возврате восстанавливается тот же экземпляр и состояние. В каждый момент видна только вершина каждого слоя. Попап не скрывает основное окно, но ввод разрешён только верхнему непустому слою. Собственные CanvasGroup не должны включать ignoreParentGroups и обходить это правило.

```csharp
await uiService.Back();                       // Назад в верхнем непустом слое.
await uiService.Back(UiLayer.Popups);         // Назад только в истории попапов.
await uiService.BackTo<MenuPresenter>();      // К меню, удалить более поздние окна и верхние слои.
await uiService.BackToDefault();              // Только основное окно по умолчанию, без попапов.
await uiService.BackToDefault(UiLayer.Popups); // Начальное состояние слоя попапов.
```

Back удаляет вершину выбранного слоя и показывает предыдущую запись. Единственное окно, зарегистрированное как default своего слоя, Back не закрывает. В слое без default последняя запись может быть закрыта: например, Back из первого попапа оставляет слой пустым. Явный Close<T> может удалить даже default-окно. Закрытие скрытой записи удаляет только её, не меняя текущую вершину.

BackTo<T> сначала проверяет наличие типа в истории его слоя. Если его нет, возвращается ошибка без изменения истории. Если он есть, все записи над ним удаляются, и все более высокие слои очищаются. Промежуточные скрытые окна не открываются ради вызова Close: их презентеры получают OnDispose. Удаление производится по точному зарегистрированному типу презентера.

BackToDefault оставляет в указанном слое только окно, зарегистрированное с isDefault: true, и очищает слои выше. Если default отсутствует в истории, он создаётся. Если default вообще не назначен, слой становится пустым. На слой разрешён один default. Сейчас это MenuPresenter для Windows; Popups по умолчанию пуст. Слои ниже выбранного не изменяются.

История сохраняет живые экземпляры и их Addressables handles до удаления записи. Это сохраняет состояние, но увеличивает использование памяти при длинных цепочках; история не является сохранением между запусками. При необходимости отдельные сценарии должны возвращаться к default или BackTo, освобождая ненужные записи.

Для кнопок используйте общий компонент WindowNavigation на UI-prefab: подключите Button.onClick к Back или BackToDefault. Для Back можно выбрать верхний непустой слой либо конкретный слой, для BackToDefault — слой назначения. Компонент получает IUiService через Zenject. Ни порядок закрытия окон, ни хранение истории в Presenter фичи не требуются.

## Жизненный цикл презентера

Presenter наследуется от `WindowPresenter<TView>`, где TView — интерфейс представления. Зависимости модели и действий приходят через конструктор, а View становится доступна в OnInitialize. Обращаться к View из конструктора нельзя.

Последовательность нормального открытия:

1. Привязка View и отключение ввода.
2. OnInitialize, событие Initialized.
3. Событие Opening, await OnOpening.
4. Анимация открытия View.
5. IsOpen становится true, await OnOpened.
6. Включение ввода, событие Opened.

Последовательность нормального закрытия:

1. IsOpen становится false, ввод отключается.
2. Событие Closing, await OnClosing.
3. Анимация закрытия View.
4. OnClosed, событие Closed.
5. Если окно удаляется из истории — OnDispose, уничтожение View и освобождение ассета. Если его перекрывает новое окно того же слоя — View деактивируется и экземпляр сохраняется.

Методы Initialize, OpenAsync, CloseAsync, Suspend и Dispose базового презентера вызывает инфраструктура. Код фичи переопределяет protected-методы OnInitialize, OnOpening, OnOpened, OnClosing, OnClosed и OnDispose. OnInitialize выполняется один раз на экземпляр, OnOpening и OnOpened — при каждом показе, в том числе возврате из истории. Подписки устанавливаются в OnInitialize и снимаются в OnDispose. OnClosed означает завершение скрытия, а не обязательное уничтожение. Вызов base нужен только при наследовании от промежуточного класса с дополнительной логикой.

Асинхронные hooks получают CancellationToken. Навигация выполняется из действий пользователя или координаторов, вне lifecycle-hooks. Нельзя ждать Open, Close или Back внутри lifecycle-hook: переход ещё не завершён. Сервис обнаруживает вложенную навигацию и возвращает ошибку вместо зависания. Hooks отвечают за состояние и поведение своего окна.

История конкретного слоя изменяется после успешного показа назначения. При ошибке или отмене перехода новый экземпляр освобождается, а прежнее окно восстанавливается; ошибка восстановления возвращается вместе с исходной. Это не отменяет произвольные побочные эффекты feature-hooks. BackTo и BackToDefault сначала выполняют переход в целевом слое, затем очищают более высокие слои; это последовательность переходов, не общая транзакция. Если очистка верхнего слоя прервалась, уже завершённые изменения нижнего не откатываются. Dispose UiService отменяет операции и освобождает все экземпляры, включая скрытые и открывающиеся, без анимаций. В публичном IUiService остаются только операции оконной навигации.

## Представления и анимации

Интерфейс View наследуется от IWindowView и добавляет события и методы конкретной фичи. Unity-представление наследуется от WindowView. В базовой View есть CanvasGroup и плавное появление/исчезновение по времени, независимому от timeScale. Длительности задаются в Inspector. PlayOpenAnimation и PlayCloseAnimation можно переопределять для собственных анимаций; реализация должна учитывать CancellationToken и завершать Task после анимации.

View отображает переданное состояние и сообщает о действиях пользователя. Она не принимает игровые решения и не управляет другими фичами. Presenter меню подписывается на PlayRequested, SettingsRequested, QuitRequested в OnInitialize и снимает подписки в OnDispose.

## Слои и сборки

| Слой | Ответственность |
| --- | --- |
| UI/Runtime — CardGame.UI | IUiService, IWindowView, базовые презентеры и жизненный цикл, без Unity и Zenject |
| UI/Unity — CardGame.UI.Unity | Общая Unity View и анимации |
| Services/Contracts | Интерфейсы загрузки JSON, ассетов и сцен; владение ассетами и экземплярами View |
| Infrastructure | Реализации сервисов, реестр окон, загрузка prefab и управление экземплярами |
| Meta | Меню и будущие фичи вне игрового процесса |
| Core | Будущие игровые механики; пока только архитектурное направление |
| Application | GameInstaller, запуск приложения и координация взаимодействий фич |

Направления зависимостей:

```text
Application → Infrastructure → Services.Contracts, UI, Zenject, Addressables
Application → Meta.Menu.Unity → Meta.Menu → Meta.Menu.Contracts
Meta.Menu → UI
Meta.Menu.Unity → UI.Unity → UI
```

Чистые Runtime и Contracts сборки фич не ссылаются на Unity, Zenject или реализации инфраструктуры. Сервис UI не знает типов MenuPresenter и MenuView: они встречаются только в регистрации Application. Сборки проекта используют autoReferenced: false; новые зависимости добавляются явно.

## Связь между фичами

Потребитель объявляет нужные ему действия в узком порту. Меню использует IMenuActions: PlayAsync, OpenSettingsAsync и Quit. Реализация MenuActions находится в Application. Первые два действия пока показывают сообщение о неподключённом сценарии; Quit закрывает player. В Editor Application.Quit не завершает Play Mode.

Для команды или запроса результата используйте типизированный метод, для длительной операции — Task. Для чтения состояния передавайте read-only интерфейс. Для уведомлений о свершившихся фактах используйте события конкретной фичи; владелец подписки обязан её освободить. Обязательные команды не следует скрывать в общей шине событий.

Реализации фич не ссылаются друг на друга. При необходимости разрешена зависимость от Contracts другой фичи, если граф остаётся ацикличным. Сценарии между фичами связываются координаторами Application. Отдельный координатор только ради создания View и Presenter не нужен. Глобальный Service Locator, общий Resolve из игровой логики и универсальный Shared не используются.

## Конфиги и загрузка ресурсов

JSON-конфиги загружаются JsonConfigService через IAssetService по адресу Addressables. Тип конфига — обычный Serializable-класс с IConfig.Validate(). JsonUtility десериализует поля, после чего вызывается валидация и освобождается handle TextAsset. Сервис не кэширует результаты. Реальные игровые конфиги добавляются по мере появления данных; адреса UI не дублируются в JSON.

AddressablesAssetService возвращает IAssetLease. Dispose идемпотентно освобождает handle через Addressables.Release. Начатая загрузка завершается перед сообщением об отмене и освобождением handle. Все Unity-операции выполняются на главном потоке.

UiViewLoader — внутренняя часть инфраструктуры. Он отвечает только за prefab и инъекцию View. UiService владеет связкой View и Presenter. При уничтожении окна сначала освобождается Presenter, затем запрашивается Destroy представления. UiAssetLifetime удерживает handle до фактического OnDestroy, чтобы bundle не выгрузился раньше экземпляра. После завершения операции отменённый или ошибочный экземпляр не сохраняется в сервисе. Уничтожать View извне вместо Close не следует.

SceneService принимает режим загрузки и флаг выбора активной сцены:

```csharp
await scenes.LoadAsync("Assets/Scenes/Location.unity",
    mode: LoadSceneMode.Additive, setActive: true, cancellationToken: token);
```

По умолчанию используются Additive и setActive: false: стартовая сцена остаётся загруженной, активная сцена не меняется. setActive: true вызывает SceneManager.SetActiveScene после завершения загрузки, выбирая новую сцену для настроек освещения и создаваемых без явного родителя объектов. Это не allowSceneActivation: загруженная сцена запускается в любом случае.

Single заменяет текущие сцены и сам делает новую сцену активной; setActive: false не отменяет это поведение Unity. Такой переход уничтожает текущий Bootstrap и его сервисы, если они находятся в заменяемой сцене. Для продолжения работы потребуется новый Bootstrap в сцене назначения либо отдельно организованный постоянный scope. После начала Single-загрузки отмена не откатывает переход: операция завершается и возвращает результат. Additive при отмене завершает загрузку и выгружает добавленную сцену. Последнюю оставшуюся сцену Unity нельзя выгрузить через ReleaseAsync — её заменяют следующим переходом.

## Zenject и Addressables

Zenject 9.1.0 установлен embedded-пакетом в Packages/com.modesttree.zenject; версия, commit и лицензия указаны в его README. Addressables 2.11.2 подключён через Unity Package Manager. Регистрации живут в GameInstaller, scope — SceneContext стартовой сцены. GameBootstrap получает ServiceLifetime и отложенную зависимость IUiService, открывает MenuPresenter и в обычном OnDestroy вызывает services.Dispose(). Отложенное создание UI начинается после передачи владельца в Bootstrap: уже созданные зависимости будут доступны для очистки даже при ошибке запуска.

Группа Addressables UI содержит Assets/GameContent/UI/Menu.prefab с уникальным адресом ui/menu и меткой ui. Используются локальные пути сборки/загрузки и Pack Separately. Для нового окна нужно зарегистрировать prefab в этой группе, назначить стабильный адрес и добавить одну регистрацию в инсталлере. Путь к файлу можно менять без изменения адреса.

Для запуска откройте Assets/GameContent/Scenes/Bootstrap.unity. Для работы в редакторе без bundles используйте Use Asset Database. Перед выпуском player соберите Addressables content через Groups → Build → New Build → Default Build Script или включите сборку контента вместе с player. Настройки групп, схемы и meta-файлы сохраняются в репозитории. Скрипты первоначального сетапа и тесты проекта не добавляются.

## Время жизни сервисов

IDisposable реализуют конкретные сервисы, а не их общие интерфейсы. GameInstaller регистрирует каждый созданный экземпляр через OnInstantiated в ServiceLifetime. Этот объект принадлежит GameBootstrap и хранит экземпляры в порядке создания. Dispose освобождает их в обратном порядке и продолжает очистку при ошибках отдельных сервисов. Не созданные ленивые зависимости ради очистки не создаются.

Zenject отвечает за создание и инъекцию, Bootstrap — за завершение жизни сервисов. IDisposable отдельно не регистрируется в Zenject, чтобы не было двух владельцев очистки. Новый сервис с ресурсами нужно регистрировать через BindService в инсталлере. Dispose должен быть идемпотентным; новые операции после него запрещены.

Dispose синхронно отменяет операции и освобождает доступные ресурсы, без ожидания и анимаций. Отложенные Destroy, выгрузка сцен и уже начатые загрузки Unity заканчиваются асинхронно; сервисы завершают их очистку внутри существующих операций. Handle ассета, уже переданный владельцу через lease, остаётся у этого владельца до Dispose lease: prefab удерживается до фактического OnDestroy его экземпляра. При завершении процесса выполнение оставшихся асинхронных операций не гарантируется.

## Добавление новой фичи

Создайте каталог Meta/<Feature> или Core/<Feature>. В Runtime разместите Model, интерфейс View и Presenter; в Unity — представление; в Contracts — только нужные внешние порты и DTO. Model содержит правила и состояние, без MonoBehaviour и UI. Для окна наследуйте Presenter от WindowPresenter<TView>, View — от WindowView, а интерфейс View — от IWindowView. Настройте prefab, адрес и регистрацию в инсталлере. Привяжите зависимости модели и действий в Zenject. Реализуйте нужные lifecycle-hooks и освобождение подписок. Для фич без UI общий оконный презентер не требуется.
